# CANN 安装权限规范

为 CANN（Compute Architecture for Neural Networks）制定既不影响使用、又满足最小权限原则的安装权限规范。

| 项目 | 内容 |
|------|------|
| 文档版本 | v1.0 |
| 制定日期 | 2026-07-22 |
| 文档状态 | 定稿 |
| 适用范围 | Linux 下 CANN 安装（root 或普通用户安装、多用户共享使用） |

**目录**:
- 第一部分　规范制定原则
- 第二部分　场景与权限规范
- 附录　权限位设计依据

---

## 第一部分　规范制定原则

| 编号 | 原则 | 说明 |
|------|------|------|
| P1 | **最小权限** | 仅授予完成功能所需的最小权限位，杜绝多余权限。区分"需内核/解释器执行的文件"（给 `x` 位）与"仅被读取的文件"（不给 `x` 位），动态库、静态库、头文件、配置、文档等被读取而非执行的文件不设执行位。 |
| P2 | **可用性优先** | 权限设置以不阻断正常使用为前提。目录需向使用者开放遍历位(`x`)与读位(`r`)以保障可达性，文件层按 P1 仅按需授予执行位（目录的遍历可达性不低于其内文件的可访问性）。 |
| P3 | **按使用者范围分层** | 按使用者范围分层：①所有用户可用、②仅安装者+安装属组可用，其他用户不可用。分别用 `other` 位与 `group` 位控制，不用的范围对应位清零。 |

## 第二部分　场景与权限规范

### 2.1 场景定义

| 场景 | 安装者 | 可用范围 | 控制策略 |
|------|--------|----------|----------|
| **场景1** | root | 系统内所有用户均可读、执行安装内容 | `other` 位向全部用户开放 |
| **场景2** | 普通用户（默认） | 仅安装者本人及其属组成员可读、执行；其他用户无任何访问权限 | `group` 位向属组开放，`other` 位全部清零 |
| **场景3** | 普通用户（`--install-for-all`） | 系统内所有用户均可读、执行安装内容 | `other` 位向全部用户开放 |

> **举例说明**:<br>root 用户安装为场景1，所有用户可用。<br>普通用户 A（属组 g1）安装：默认（场景2）下仅 A 及 g1 组成员可用；加 `--install-for-all`（场景3）下所有用户可用。

**场景间关系**: 场景2 → 场景3（普通用户安装时加 `--install-for-all`）：开放 `other` 位（如 750→755、640→644），将可用范围从安装者+属组扩大到所有用户；符号链接 777 不变。

### 2.2 权限对照表

> **属主/属组**: 场景1 为 `root:root`，场景2/3 为安装者:安装属组。场景1 与场景3 权限值相同，仅属主/属组不同。

| 资源类型 | 场景1 | 场景2 | 场景3 | 说明 |
|----------|--------|--------|--------|------|
| 所有目录 | 755 | 750 | 755 | — |
| **可执行程序**（ELF 二进制） | 755 | 750 | 755 | — |
| **Python/Shell 脚本**（`.py`/`.sh`） | 755 | 750 | 755 | 统一可执行（见 A.4） |
| **安装/卸载脚本** `install.sh`/`uninstall.sh` 等 | 744 | 740 | 744 | 仅安装者可执行，防止非授权用户触发卸载/重装 |
| **其他文件** | 644 | 640 | 644 | `.so`/`.a` 等，无 x 位（见 A.3） |
| **符号链接** | 777 | 777 | 777 | 内核默认；Linux 不检查符号链接自身权限，实际访问控制由目录与目标文件决定 |

### 2.3 使用者能力矩阵

| 场景 | 使用者 | 遍历目录 | 执行程序/脚本 | 加载 .so | 读取头文件/配置/文档 | 修改/删除文件 |
|------|--------|----------|--------------|----------|---------------------|--------------|
| 场景1/3 | 安装者 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 场景1/3 | 其他用户 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 场景2 | 安装者 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 场景2 | 安装属组成员 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 场景2 | 其他用户 | ❌ | ❌ | ❌ | ❌ | ❌（目录 750 阻断遍历） |

> **注**: 安装/卸载脚本（场景1/3 为 744、场景2 为 740）仅安装者可执行，其他用户不可执行。

## 附录　权限位设计依据

### A.1 为什么不采用防篡改（去除写位）

防篡改设计指去除安装内容的写位（含安装者），使所有人只读，修改须先 `chmod u+w` 恢复写位。本规范不采用该设计，理由如下：

| 使用者 | 防篡改的实际效果 |
|--------|-----------------|
| root 安装者 | root 绕过 DAC 检查，可直接写任何文件，有无写位均无影响，防篡改无任何防护作用 |
| 普通用户安装者 | 安装者拥有属主权限，可随时 `chmod u+w` 恢复写位后修改，防篡改不构成实质拦截，仅防止误操作 |
| 其他用户 | 场景1/3 下其他用户本就无写位，场景2 下其他用户无访问权限，标准权限已阻断写操作，与防篡改无关 |

> **结论**: 防篡改对 root 安装者无效，对普通用户安装者仅防止误操作而不构成实质拦截，对其他用户则与标准权限重复。而其代价显著：卸载/重装需"解锁→操作→重锁"流程、`.pyc` 须预编译、与包管理器不兼容。综合权衡，防护收益不足以支撑其引入成本，故不采用。

### A.2 为什么目录需要 `x` 位

Linux 中目录的 `x` 位语义为"遍历/进入"权限，而非"执行"。使用者要访问任何子路径，路径上**每一级目录**都必须有 `x` 位。故：
- 场景1/3：目录 `755`，other 有 `x`，所有用户可遍历至任意子目录。
- 场景2：目录 `750`，other 无 `x`，其他用户连根目录都无法进入，彻底阻断访问。

### A.3 为什么库文件 `.so`/`.a` 用 644/640 而非 755

| 依据 | 说明 |
|------|------|
| 加载机制 | 动态链接器 `ld.so`/`dlopen()` 与静态链接器通过**读取文件内容**加载，不调用 `execve()`，不要求文件有 `x` 位 |
| 最小权限(P1) | `.so`/`.a` 是被读取的库数据，按 P1 原则不给 `x` 位 |

> **结论**: 库文件不给 `x` 位，符合最小权限。场景1/3 为 644、场景2 为 640。`.so` 的所有加载机制（`dlopen()`、`ld.so`）均通过读取文件内容加载，不依赖 `x` 位。

### A.4 为什么 `.py`/`.sh` 脚本统一为可执行而 `.pyc` 不给执行位

`.pyc` 是 Python 解释器将 `.py` 源码编译后的字节码缓存文件，由解释器在 `import` 时**读取并加载到内存执行**，而非通过内核 `execve()` 直接执行，属"被读取的数据"，按 P1 不应授予 `x` 位。`.py`/`.sh` 脚本则可经 `execve()` 执行（带 shebang 时），统一授予可执行权限。

| 对比项 | `.py`/`.sh` 脚本 | `.pyc` 字节码 |
|--------|-----------|---------------|
| 执行方式 | 可经 `execve()` 由内核直接执行（带 shebang 时） | 仅由解释器 `import` 加载，不可 `execve()` |
| 权限归属 | 统一为可执行（场景1/3 为 755、场景2 为 750） | 按 P1 归为数据文件（场景1/3 为 644、场景2 为 640） |
| 是否带 x 位 | 是 | 否 |

> **取舍说明**: `.py`/`.sh` 统一为可执行（含被 import 的库模块）使库模块带多余 `x` 位，轻微偏离 P1。但作为文本脚本，`x` 位本身不直接导致提权风险（执行仍需解释器），且统一规则大幅降低维护成本、保证 `bin/` 符号链接可用（`bin/` 下符号链接指向脚本，脚本无 x 位则链接无法直接执行）。**此为规范明确允许的 P1 例外，不构成其他场景偏离 P1 的先例。** `.pyc` 则按数据文件处理，不给 x 位。
